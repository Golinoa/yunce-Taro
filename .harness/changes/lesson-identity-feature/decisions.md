# 关键决策与原因

> 约定：能按设计自决的**直接定**，只在真正需要业务判断时才上报。本页记录"定了什么、为什么"。

## D1 · 身份用「排课编号」而不是「时段」

- **决定**：一节课身份 = `(Schedule.id, lessonDate)`；编号优先，时段只兜底。
- **依据**：调课只写 `TemporaryReschedule`、**从不改 `Schedule` 行** ⇒ 编号稳定；时段会变且有歧义（同班同天多节）。
- **为什么不用时段**：两起事故的根因都是时段当身份。

## D2 · 不新造课次编号

- **决定**：直接用现成的 `Schedule.id`，不建 `LessonOccurrence` 表。
- **依据**：现在课表是"规则 + 调课实时叠加"推导出来的，没有课次实体 ⇒ 新建等于重建排课域，改动量数倍。
- **未来**：真要引入课次概念时，排课编号可平滑升级，**本次不挡路**。

## D3 · 记录与预约的兜底**故意不一样**

| 数据 | 有没有时段列 | 缺编号时 |
| --- | --- | --- |
| 记录 `LessonRecord` | ❌ 没有 | **不区分**（宁可多显示，不能吞记录） |
| 预约（试听/补课） | ✅ 有 | **回落比时段**（变严不变松，绝不再"整天乱挂"） |

- **依据**：记录没有时段可比，只能放行；预约有时段就比时段。
- ⚠️ **不可把两者写成同一套**，否则要么吞记录、要么整天乱挂。

## D4 · 从「班级列表」入口：让老师指明「第几节」

- **决定**：采用 **方案 A（选班后弹「第几节」）**，不采用"入口改成课次列表"，也不采用"不加界面"。
- **依据**：不管用哪种身份，只要页面不知道是哪一节，身份就定不了 ⇒ 这一步**无法回避**。
  方案 A 改动集中在点名页、当天仅 1 节时不打扰；方案 B 要重做选班界面；方案 C 等于不解决。

## D5 · 补课表加外键（附加服务层校验兜底）

- **决定**：`MakeupBooking.scheduleId` **加外键（删除策略 SET NULL，与 `LessonRecord` 同口径）**；
  同时服务层落库前校验编号存在，**查不到就置 `null`**。
- **依据**：加外键有引用完整性收益；但会带来"传错编号 ⇒ 写库失败"的新风险 ⇒ 用服务层兜底抵消。
- **例外**：`LeadBooking.referenceScheduleId` **不加外键**（邀请流程可能写入未落库的编号，加 FK 会写失败），保持软引用。

## D6 · 不做「删除排课规则的禁止保护」

- **决定**：不加。
- **依据**：用户口径（2026-09-30）——"删除排课规则，已有的流水账不能丢失；流水账只要对得上**课程名称 / 老师 / 操作人**即可"。
  已核实：删规则走 `SET NULL`，记录行保留；三项均来自记录自己的列 / 班级表，**不依赖排课表**。

## D7 · 不做「同日调课的时间冲突校验」

- **决定**：本次不做，登记为已知问题。
- **依据**：不影响"哪一节"的判定（编号已能区分）；补它要先定义"什么算冲突"（老师 / 教室 / 班级 + 例外），
  属独立一块，混进本次会扩大回归面、且有误挡老师正常操作的风险。

## D8 · 日期参数名 bug 一并修

- **决定**：修。`booking/index.tsx` 与 `lead-detail/index.tsx` 传 `date=`，而点名页只读 `lessonDate` ⇒ **打开的是"今天"**。
- **依据**：明显缺陷、低风险，就在这次顺手做掉。

## D9 · 顺带修：流水账解不出「老师 / 操作人」

- **决定**：纳入本次。后端两处记录序列化补老师字段；前端去掉 `teacher_id: ''` 硬编码、补 `operator_teacher_id` / `assistant_teacher_id`。
- **依据**：核对用户验收三项时发现的真缺陷 —— **现在就显示「未知教师」**，不是删规则之后才有。
- **特点**：与"哪一节"无关，**可独立先做、独立回归**。

## D10 · 块 0 复核：两处**语义放宽**，已确认实际输入下等价

收敛到唯一真源时，新实现相对旧实现有两点放宽（对抗式复核逐条对过）：

1. **日期比较改为归一后比较**（`normalizeLessonDate` 取前 10 位），旧实现是严格 `!==`。
   ⇒ 若记录 `lesson_date` 是 datetime 串、目标是 `YYYY-MM-DD`，新实现会判为同一天（旧实现不会）。
2. **归属对象支持私教**（`studentId`），旧实现只比 `classId`；且两边都无归属时新实现返回 `false`
   （旧实现在 `target.classId === undefined` 且 `record.class_id === undefined` 时会放行）。

**为什么安全**：前端 `mapBackendLessonRecord` 已把 `lesson_date` 归一成 10 位；
现有调用方传入的 target **都带 `classId`**（私教路径尚未接入）。⇒ 现有输入下行为完全一致。

**验证**：受影响单测全绿（`lesson-record-scope` / `schedule-card-build` / `schedule-danger-logic` /
`lesson-attendance-load`，共 42+ 条），`tsc` 0 错。

⚠️ 若后续有调用方开始传 `studentId` 或传未归一的日期，行为会变化 —— 那时按新口径（更正确）走，不必回退。
