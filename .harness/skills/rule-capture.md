# Skill: 规则与技能沉淀（rule-capture）

> 回答：**什么时候把一次经验写成 rules / skills？写哪？怎么验证？**

## 触发时机

### 写进 `rules/`（约束，什么不能做）

出现以下任一情况，应沉淀为规则：

- [ ] 同一个问题在 **Code Review 中被提出 3 次以上**
- [ ] 一次真实事故（线上 / 测试 / 用户反馈）暴露出的坑
- [ ] 修复某个 bug 后，发现根因是可避免的常见错误

### 写进 `skills/`（流程，按什么步骤做）

- [ ] 一个操作被**重复执行 3 次以上**（如"新增弹窗""修复某类 bug"）
- [ ] 流程有固定步骤、固定模板、固定验证点
- [ ] 另一个人从头做这件事需要摸索才能完成

### 不要沉淀

- 一次性任务、临时排查
- 会随版本频繁变动的实现细节（写 wiki 不写 skill）
- 与现有规则重复的内容（先查索引再写）

## 写哪（归属判断）

| 内容类型 | 去向 |
| --- | --- |
| 禁令 / 硬性要求 | `rules/NN-*.md` |
| 步骤流程 / 模板 | `skills/*.md` |
| 事实清单（有什么、在哪、长什么样） | `wiki/*.md` |
| 任务进展 | `changes/<feature>/` |

## 规则格式（三要素，缺一不可）

每条规则必须让读到的人能自愈，不需要再问：

```md
❌ [什么错了 / 反例]
✅ FIX: [怎么改，给代码片段]
📖 See: [哪个文档有详细说明]
```

## 沉淀后动作

- [ ] 在 `rules/README.md` 或 `skills/README.md` 索引中登记
- [ ] 重签文件的 `last_updated`
- [ ] 更新适配层（`.cursor` / `codex.md`）**不需要**——它们只指向 AGENTS.md
- [ ] 若规则可机械化 → 评估加 ESLint 自定义规则（`.harness/rules/README.md` 记录）

## 验证

- [ ] 新规则能追溯到一个真实事故或反复 Review 意见（source 字段写明）
- [ ] 与现有规则无重复、无冲突（冲突只保留一条）
- [ ] 三要素完整
