## 4. 同缺陷类全仓盘点 —— 已全部收敛（用户「一起修复」，修法：提示播完 → 退页）

判据：`Taro.hideToast()` 出现在成功 `showToast` 之后；或 `await runFlow(...)` 位于跳转之前。

**统一修法**

- A 类：`showToast(…, duration: SUCCESS_TOAST_MS)` → `setTimeout(退页, SUCCESS_TOAST_MS)` → `void (async () => runFlow(...))()`。退页不再依赖订阅 flow。
- B 类：本无退页动作，故 `setTimeout(() => { Taro.hideToast(); void runFlow(...) }, SUCCESS_TOAST_MS)` —— 等提示播完再 hide，然后触发订阅弹框。
- `lesson-form` 的 helper 保留 `duration` 参数作为退页延时（`Math.max(0, duration)`），让延时与 toast 时长天然一致。

**C 类 —— 不构成问题（勿误判）**

- `components/my-todos/AddCustomTodoPopover/index.tsx:177` 的 `await runFlow('E12')`：E12 在 `runFlow` 内**直连 `requestAuthAndReport`、不经 `openPrompt`**（`subscribe-message.ts:314`），不会挂起。
- `services/calendar-sync.ts:386` 的 `await runFlow('E19')`：无 UI 跳转依赖。
- `utils/post-save-navigation.ts:45` 的 `hideToast()`：在 toast 播满 1500ms **之后**才调用，属设计内。

> ⚠️ **判定要点**：`Taro.hideToast()` 并非一律有罪——它同样用于关闭 `showLoading`（微信里 showLoading/showToast 共用同一通道）。
> 只有「成功 `showToast` 紧跟着 `hideToast`」才是缺陷；「`showLoading` 之后 `hideToast`」是正确用法。勿一刀切。
>
> 收敛后复扫：全仓已无「紧跟成功 toast 调 hideToast」的写法，剩余 5 处 `Taro.hideToast()` 全部位于 `setTimeout(…, SUCCESS_TOAST_MS)` 内（或 `post-save-navigation` 的设计内调用）。
