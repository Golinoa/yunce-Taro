### 源码层面的两条硬约束（每轮都要用）

1. **全局 `retry: false`**（`src/app.tsx:58`）→ 任何真实 reject 会**立刻**变 `status:'error'`。
   所以 `pending/idle + error:null` **只可能**来自 `query-core/query.js:220` 的
   `onCancel` → `CancelledError.revert` 分支（`setState({...revertState, fetchStatus:'idle'})`）。
2. `query-core` 里 `revert:true` **只有两处**：`query.js:138`（`removeObserver`，需 observers=0）
   与 `queryClient.js:129`（`cancelQueries()`，全项目无调用）。
   → 两处都被排除时，说明**现有埋点覆盖不到真正的取消源**，必须换观测手段，而不是再加同类埋点。
3. **`Query.fetch()` 是异步函数：抛错会变成 rejected promise，且不经过 status → error 的路径**。
   所以「query 完全没反应、连报错都没有」也可能是**库内部依赖了小程序不支持的原生 API 而抛错**。
   `query-core@5.102.8` 全库只有一处 `new AbortController()`（`query.js:172`，在 `fetch()` 最前面），
   而小程序运行时**没有 `AbortController`** → 直接 `ReferenceError`。
   **教训：库依赖的原生 API 也要进候选清单**（`AbortController` / `AbortSignal` / `structuredClone` /
   `queueMicrotask` / `EventTarget` …），排查时用 `typeof` 逐个验证。

## R7 · 根因确认：小程序缺 `AbortController`（已修复）

- **buildId**：`students-debug-20260923-06`
- **现象**（`-05` 真机日志，决定性证据原文）：

```
[students-query-stall] attempt:1  queryFnRuns:0  onlineManagerIsOnline:true
  focusManagerIsFocused:true  qStatus:"pending"  qFetchStatus:"idle"  qObservers:1
  qFetchFailureCount:0  qFetchFailureReason:null  qDataUpdateCount:0  qErrorUpdateCount:0
  qNetworkMode:null  qHasBehavior:false  qHasQueryFn:"function"  qIsDisabled:false  qIsActive:true

[students-manual-fetch] attempt:1  errName:"ReferenceError"
  errMessage:"AbortController is not defined"  errRevert:null  errSilent:null  queryFnRuns:0

[students-direct-fallback] attempt:2  count:4  queryFnRuns:0
[students-query-result] status:"success"  fetchStatus:"idle"  studentCount:4     ← 兜底生效，列表出数据
```

- **假设**：R5 已排除所有「谁 cancel 了 query」的方向；本轮提出：
  **`fetch()` 根本没走到 cancel 那一步，而是更早就抛错了。**
- **验证方式**：绕过 observer 直接 `queryCache.find(key).fetch()`，把真实错误对象原样记录（R6 已埋好）。
- **结论**：✅ **成立 —— 根因确认。**

  **机制**：`@tanstack/query-core@5.102.8` 的 `Query.fetch()`（`build/modern/query.js:172`）
  **第一件事**就是 `const abortController = new AbortController()`，且这是**全库唯一一处**引用
  （已 grep 确认：`build/modern/*.js` 仅此一处；产物 `dist/` 内 `AbortController` 也只在 `vendors.js`）。
  微信小程序运行时**不提供 `AbortController`** → 构造时抛 `ReferenceError`：

  - 异常发生在 `queryFn` 调用**之前** → `queryFnRuns` 恒 0、后端收不到任何请求；
  - `fetch()` 是 async 函数，抛错变成 **rejected promise**，而 `QueryObserver` 未捕获 →
    状态既不前进也不报错，永久停在 `status:'pending' + fetchStatus:'idle'`；
  - 这也解释了为什么 R1–R5 找「取消源」全都落空 —— **根本没有取消，是抛错了**。

  附带解释「为什么首页看起来正常」：首页 `useQuery` 先命中缓存（`staleTime:30s`）时不发请求，
  掩盖了故障；学员页 `useInfiniteQuery` 有 `refetchOnMount:'always'` 必发首屏请求，所以最先暴露。
  **该缺陷实际影响所有 TanStack Query 请求，是全局性问题，不只是学员页。**

- **改动文件**：
  1. **新增 `src/utils/abort-controller-polyfill.ts`**：精简 `AbortSignal` / `AbortController` 实现
     （覆盖 `aborted` / `reason` / `addEventListener('abort', fn, {once})` / `removeEventListener` /
     `throwIfAborted` / `onabort` / `abort(reason?)`），**原生存在时不覆盖**。
     刻意手写而非引入 `abort-controller` + `event-target-shim`（主包仅剩 ~60KB 余量）。
  2. **`src/app.tsx`**：`import { ABORT_CONTROLLER_POLYFILL_INSTALLED } from '@/utils/abort-controller-polyfill'`
     （模块顶层即安装），并加**一次性启动自检**埋点 `abort-controller-env`
     （`installed` / `hasAbortController` / `hasAbortSignal` / `hasGlobalThis`）——
     以后一眼就能确认 polyfill 是否生效。
  3. **`src/package-student/pages/students/index.tsx`**：把 R6 的重诊断探针（环境开关全量 dump +
     手动 `query.fetch()`）收简为**安全网**：停滞时补拉 1 次，仍停滞则直接走 service 拉数写缓存。
     根因既已修复，此网只防「同类静默失败」再次造成永久空白。
  4. **新增 `src/utils/abort-controller-polyfill.test.ts`**：11 个用例覆盖
     初始未 abort / `abort()` 幂等与 reason / `{once:true}` 只触发一次 / `removeEventListener` /
     `onabort` / `throwIfAborted` / 非 abort 事件名忽略 / 安装与不覆盖原生。

  - **59 文件 / 336 测试全绿**（325 原有 + 11 新增）
  - 编译成功：主包 **1477.8KB / 1536KB**（polyfill 仅 +1.7KB），117 个分包 chunk requires 通过，

| `state.fetchStatus` | `'idle'` | `'idle'` |
| `state.error` | `null` | `null`（**静默**） |
| 抛出的异常 | `ReferenceError: AbortController is not defined` | 手动 `query.fetch()` 报同一错误 |
| `fetchStatus` 变化序列 | `[]`（**一次都没变过**） | 见下方「保留的不一致」 |

→ **问题真实性成立**：缺 `AbortController` 足以让 `queryFn` 零执行、状态永久停在 `pending/idle`，
且**不产生任何 error**（抛出点在 `dispatch({type:'fetch'})` 之前，所以连 `fetching` 都不会进入）。

**实验 ② 证明修复**：同一 query 装上 polyfill 后 → `queryFn` 调用 **1** 次、`status:'success'`、
拿到 1 页数据。→ **修复有效**。

**保留的不一致（如实记录，不硬凑解释）**：
生产 `-05` 日志里 `fetchStatus` 先出现 `fetching`、再回到 `idle`，而实验 ① 的序列是 `[]`。
两者矛盾说明生产那一刻 `AbortController` **可能是存在的**，即可能另有第二条机制：
> `cancel({revert:true})` → `onCancel` 里 `abortController.abort()` → 随后
> `addConsumeAwareSignal` 读到「已 aborted 的 signal」→ `cancelled = true` →
> `infiniteQueryBehavior.fetchPage` 直接 `Promise.reject(signal.reason)` →
> **queryFn 被整体跳过**（同样表现为 `queryFnRuns:0`）。
> 或该 `fetching` 是微信开发者工具「自动热重载」重建沙箱造成的观测污染。

**两种机制都已覆盖**：①→polyfill 移除该依赖；②→停滞安全网（补拉 1 次，仍失败则直接拉数写缓存）。
并且已加诊断字段 **`hasAbortController`**：复发时若为 `true` 即锁定机制 ②，为 `false` 则是 polyfill 未生效。
