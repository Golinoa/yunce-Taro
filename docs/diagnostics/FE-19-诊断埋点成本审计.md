# FE-19 · 诊断埋点的成本审计与修复

> 触发：用户提问「刚才修复时加了很多输出日志，会影响代码包大小和运行速度吗」。
> 结论：**包大小影响可忽略（约 6.8 KB）；运行速度上原本有真 bug，已修复。**
> 涉及文件：`src/utils/local-debug.ts`。buildId `students-debug-20260923-17`（未 bump，行为对调试包等价）。

---

## 1. 包大小：可忽略

埋点统一入口是 `src/utils/local-debug.ts` 的 `reportLocalDebug`，全站 **28 个调用点**。

测量方式：扫描 `dist/**/*.js`，对每个 `hypothesisId:` 出现处做花括号配平，取出完整的参数字面量长度。

| 文件 | 占用量 |
| --- | --- |
| `package-student/pages/students/index.js` | 3 140 B |
| `common.js`（主包） | 1 999 B |
| `pages/home/index.js`（主包） | 817 B |
| `package-course/pages/package-form/index.js` | 411 B |
| `package-student/pages/student-form/index.js` | 395 B |
| `app.js`（主包） | 287 B |
| **合计** | **6 949 B（6.8 KB）** |

- 模块实现本身只占约 **0.7 KB**（`common.js` 里唯一一处 `YUNCE_DEBUG` 字符串，全 dist 仅 1 个文件含该字符串）。
- 真正的体积是 **28 个调用点的 `{hypothesisId, location, msg, data}` 字面量**，各自留在所在 chunk 里。
- 主包合计约 2.3 KB / 1.5 MB ≈ **0.15%**；微信上传还会再压缩，实际更小。

⇒ **结论：不是需要为它专门清理的量级。** 想彻底归零也很简单，见第 4 节。

## 2. 运行速度：原来是真 bug（已修）

### 2.1 根因：门禁写在了副作用之后

修复前的语句顺序：

```
建 event → Taro.getStorageSync → Taro.setStorageSync → console.warn
        → if (!ENABLE_LOCAL_DEBUG) return  ← 门禁在这里
        → Taro.request（唯一被挡住的一步）
```

也就是说，`ENABLE_LOCAL_DEBUG` 这个「默认关闭」的开关**只关掉了网络上报**，
storage 同步读写和 console 输出在**任何构建下都会执行**。

编译产物铁证（修复前 `dist/common.js`）：

```js
function h(e){ ... try{ u().getStorageSync(f); u().setStorageSync(f,[...].slice(-50)) }catch(e){}
  console.warn("[YUNCE_DEBUG] ...", h), c && u().request({...}).catch(function(){}) }
//                                          ↑ 门禁 c 只出现在 request 前面
```

每次调用固定成本 = **1× `getStorageSync` + 1× `setStorageSync`（写的是最多 50 条事件的数组，每次整体序列化）+ 1× `console.warn`**。

而调用点密集落在热路径上：

| 位置 | 调用次数 | 频次 |
| --- | --- | --- |
| `utils/request.ts` | 2 | **每个请求** |
| `utils/route-guard.tsx` | 7 | **每次路由鉴权** |
| `components/home/KingKongSection/index.tsx` | 2（含 render 体内 1 处） | **每次 render** |
| `pages/home/index.tsx`、`StudentQuickList` | 各 1 | 首页渲染 |
| `package-student/pages/students/index.tsx` | 10 | 学员页各阶段 |
| 两个 `use*Form.ts` | 各 2 | 表单提交 |
| `app.tsx` | 1 | 启动一次 |

⇒ 同步 storage IO 叠加高频调用，是真实的卡顿来源。

### 2.2 附带发现：常量没被折叠

```ts
// ❌ 原写法
const ENABLE_LOCAL_DEBUG =
  typeof process !== 'undefined' && typeof process.env !== 'undefined'
    ? process.env.TARO_ENABLE_LOCAL_DEBUG === 'true'
    : false;
```

`process.env.TARO_ENABLE_LOCAL_DEBUG` 会被 `config/index.ts` 的 DefinePlugin **在打包时**替换成字面量，
但外层那圈 `typeof` 运行时判断让整个表达式**无法折叠为常量**，产物里残留：

```js
c = "undefined" !== typeof process && "undefined" !== typeof process.env
```

## 3. 修复

`src/utils/local-debug.ts`：

```ts
// 1. 构建期可折叠常量（与同项目 utils/logger.ts:78 的既有写法一致）
const ENABLE_LOCAL_DEBUG = process.env.TARO_ENABLE_LOCAL_DEBUG === 'true';

// 2. 运行环境探测只服务于「要不要发本机调试请求」
const CAN_POST_TO_DEBUG_SERVER = ENABLE_LOCAL_DEBUG && typeof process !== 'undefined';

export function reportLocalDebug(payload): void {
  if (!ENABLE_LOCAL_DEBUG) return;   // ← 提到第一行，在所有副作用之前
  ...storage...
  ...console.warn...
  if (!CAN_POST_TO_DEBUG_SERVER) return;
  ...Taro.request...
}
```

第 2 条是刻意保留的：微信小程序运行时没有 `process`，这个上报本来就没发出去过；
保持原样可以避免给调试期引入 28 处必然失败的请求噪声。

## 4. 验证：terser 死代码消除实验

因为沙箱里带 `TARO_OUTPUT_DIR` 的构建会被提前终止（见备注），改用**等价实验**复现 webpack 生产构建的三步：
DefinePlugin 文本替换 → esbuild TS 转译 → terser 压缩（`compress.passes=2` + `mangle`）。

同时为排除 ESM 导出语义对 DCE 判定的干扰，把模块体包成 IIFE 并标记函数被外部引用。

| 场景 | 修复前 | 修复后 |
| --- | --- | --- |
| **生产构建**（未设 `TARO_ENABLE_LOCAL_DEBUG` ⇒ `"false"`） | 1 496 B<br>`YUNCE_DEBUG` ✅存在<br>`getStorageSync` ✅存在<br>`console.warn` ✅存在<br>`127.0.0.1` ✅存在 | 589 B（全是 esbuild 辅助函数脚手架的残留）<br>`YUNCE_DEBUG` ❌**已删除**<br>`getStorageSync` ❌**已删除**<br>`console.warn` ❌**已删除**<br>`127.0.0.1` ❌**已删除** |
| **调试构建**（`=true`） | 1 500 B，全部保留 | 1 478 B，全部保留 |

修复后 **生产构建的 `reportLocalDebug` 被压成空函数**：

```js
globalThis.__keepReportLocalDebug = function ({ hypothesisId: o, location: r, msg: e, data: _ }) {};
```

⇒ **生产包零运行时开销、零调试代码体积；调试包诊断能力完全不变。**

## 5. 下一轮开工前必读（硬约束）

1. **诊断埋点的门禁必须写在函数第一行。** 任何「默认关闭」的开关都要核对它是否覆盖了**全部副作用**
   —— 最容易被漏在门禁之外的就是「日志 / 落盘」，因为网络上报通常写在最后。
2. **用 `process.env.X` 做构建期开关时不要包 `typeof` 守卫。** DefinePlugin 会把 token 替换成字面量，
   包了 `typeof` 反而让常量无法折叠、terser 删不掉死代码。直接比较即可（参照 `utils/logger.ts:78`）。
3. **加新埋点前先判断它落在哪条路径上。** render / 请求 / 路由鉴权这类热路径上的埋点，
   即使被门禁挡住，调用点的参数字面量也仍然留在包里；高频路径优先不加。
4. **生产构建 = 不传 `TARO_ENABLE_LOCAL_DEBUG`**：`scripts/build-weapp-prod.mjs` 没设该变量，
   只有 `build-weapp-dev.mjs` / `dev-weapp-dev.mjs` 设为 `true`。以后要临时关日志，构建时不带该变量即可。
5. 测量埋点包体占用要看**调用点参数字面量**，不是模块本身 —— 模块只定义一次。

## 6. 备注 / 已排除

- **已排除：管道导致构建被终止。** 首次怀疑 `| tail -N` 让任务被误判完成，实测多次带管道的构建均成功，
  **不是原因**。真正变量是 `TARO_OUTPUT_DIR=dist-prodtest`：两次带该变量的构建都在约 8 秒时被静默终止
  （webpack 停在 40%、只产出 `project.config.json`、exit 0 且无报错）。对比产物请勿使用该变量。
- **已排除：埋点模块被 tree-shake 掉。** `dist/app.js`（主包入口）与 `common.js` 均确认包含该模块。
- **未做：清理 28 个调用点。** 修复后生产包已无运行时代价，调用点只在调试包生效，故保留以便后续排查。
  若日后要连 `6.8 KB` 一起省掉，逐个删除调用点即可（无耦合）。
