## 二、总体结论（架构画像）

项目采用 **"中心库 + 散落独立库"的混合 Mock 架构**：

```
┌────────────────────────────────────────────────────────────┐
│  中心库  src/data/mock-database.ts (3814 行，静态数组)        │
│  组织/校区/场地/教室/用户/身份/教师/科目/班级/学员/课包/        │
│  排课/课次/请假/月统计/校区统计/薪资记录/通知                  │
└───────┬──────────────────────┬──────────────────────────────┘
        │ 共享(只读/部分写)       │ 完全不共享
        ▼                        ▼
┌───────────────┐      ┌──────────────────────────┐
│ student/home/ │      │ 独立库(各 service 私有):    │
│ auth(部分)     │      │ teacher.ts 教师+薪资       │
│ 等少量 service │      │ member-card.ts 会员卡      │
└───────────────┘      │ course-template.ts 课程模板 │
                        │ lead.ts 线索/试听           │
                        │ statistics.ts+data/mock    │
                        │ 统计 ｜ data-center.ts 数据中心│
                        │ class-booking/venue-booking │
                        │ my-course/home/card-type   │
                        │ campus/feedback/store-entry│
                        └──────────────────────────┘
```

**核心判断**：UI 已定型，但 **Mock 层"各模块各自为政"**——中心库与独立库之间、甚至同一实体的不同操作之间，读写回写策略不一致，导致跨页面数据不联动。**这是"拼凑感"的根源，不是 UI，而是数据层。**

## 三、五大核心发现（附证据）

### 🔴 P0-1 同一实体存在多份数据源（双库/三库分裂）

| 实体 | 中心库副本 | 独立库副本 | 后果 |
|---|---|---|---|
| 教师 | `mock-database.TEACHERS` | `data/teacher.ts` 自有数组 | 排课页（走 teacher service → 独立库）与班级/学员关联的教师 ID 可能对不上 |
| 学员课包 | `mock-database.COURSE_PACKAGES` | 无 | 会员卡库独立，见 P0-3 |
| 会员卡 | 无 | `data/member-card.ts` 自有 `MOCK_MEMBER_CARDS` | 办卡/充值完全与学员课包隔离 |
| 课程模板 | 无 | `data/course-template.ts` `MOCK_TEMPLATES` | 与课程分类（course-category 独立库）靠字符串 ID 弱关联 |
| 统计 | 中心库有 `MONTHLY_STATS/CAMPUS_STATS` | `data/statistics.ts` + `data/mock/` 第三套 | 统计数字不随业务流水变化 |
| 薪资 | 中心库 `TEACHER_SALARY_RECORDS` | `data/teacher.ts` 薪资模型/模板 | 薪资手工记录，不自动汇总 |

> 证据：`services/teacher.ts` 只 import `@/data/teacher`（0 处引用 mock-database）；`data/member-card.ts` 同样 0 处引用中心库；`services/statistics.ts` 用 `@/data/mock` + `@/data/statistics` 双源。

### 🔴 P0-2 写操作"假增删改"：大量 update/delete 不写回共享数组

抽样证据（`src/data/students.ts`）：

| 操作 | 实现 | 是否生效 |
|---|---|---|
| `mockCreateStudent` | `DB_STUDENTS.push(newStudent)` | ✅ 创建生效 |
| `mockUpdateStudent` | `return { ...student, ...data }`（**不写回数组**） | ❌ 假更新：页面刷新即回滚 |
| `mockDeleteStudent` | `return true`（**不移除**） | ❌ 假删除 |
| `mockCreateSchedule` | 返回新对象（**不 push SCHEDULES**） | ❌ 排课不落库：日历/记录页读不到 |
| `mockUpdateSchedule` | 只返回（不写回） | ❌ 假更新 |
| `mockCreateClass` | `return { id: 'class-…', ...data }`（**不 push**） | ❌ 新建班级列表看不到 |
| `mockUpdateClass` | 只返回（不写回） | ❌ 假更新 |
| `mockDeductPackageHours` | 只 `find` 返回原对象（**不扣 remaining_hours**） | ❌ 消课不扣课时 |

同一模式在 `data/teacher.ts`（866/876/933/977/989 多处 `return true`）、`data/lead.ts`（4+ 处）、`data/feedback.ts`（73）同样存在。

**规律**：凡"创建"大多写回（push/unshift），凡"更新/删除/扣减"大多是假操作。→ **新增数据能看见，改删扣都看不见**。

### 🔴 P0-3 核心业务闭环断裂点

**① 办卡/充值 → 学员剩余课时（双库隔离）**
- 会员卡写 `data/member-card.ts` 独立库；学员课时写 `mock-database.COURSE_PACKAGES`
- 办卡/充值后，学员视角剩余课时**不会变**（`member-card` 库与 `COURSE_PACKAGES` 无任何联动代码）

**② 消课 → 扣课时（假扣减）**
- `lesson-form` 提交会写 `LESSON_RECORDS`（✅ 课次落库），但 `mockDeductPackageHours` 不修改 `remaining_hours`
- 结果：点名/消课记录有，学员剩余课时不变 → "已消 5 节课但剩余课时没少"

**③ 排课 → 课次 → 签到（排课不落库）**
- `schedule-form` 创建排课只返回对象不写 `SCHEDULES`
- 日历/周视图按 `SCHEDULES` 渲染 → **新排的课不出现在课表里**；课次（LESSON_RECORDS）靠 lesson-form 手动建，与排课无自动生成关联

**④ 薪资 ← 课时（手工记录）**
- 薪资记录静态（`TEACHER_SALARY_RECORDS`），薪资模板/模型在 teacher.ts 独立库
- 薪资不从 `LESSON_RECORDS` 自动汇总课时费，全部依赖手工/批处理假数据 → 教师工资与实际上课数对不上

**⑤ 统计/数据中心（第三套数据）**
- `statistics.ts`/`data-center.ts` 读独立 mock → 首页"学员数/课次/营收"等数字与真实业务实体不联动

### 🟠 P1-4 状态层覆盖不足，跨页面共享靠"各页面自拉"

- 115 个页面仅 **21 个**使用 Zustand store（课程/学员/教师/薪资的核心页）
- 其余页面直接调 service 裸拉数据，无统一缓存/失效机制 → 同一数据在不同页面刷新策略不一致，容易出现"这页改了那页看不到"

### 🟡 P1-5 角色链路部分页面绕过

- `useAuth` 覆盖 49/115 页（43%），`currentContext` 角色切换存在
- 教师/家长/校长视角的数据过滤（如教师只看自己的学员）集中在少数页面，未形成全局统一的"按角色切数据域"的约定

## 四、业务链路现状（逐条打通度）

| 业务流 | 现状 | 打通度 |
|---|---|---|
| 学员：新增→列表→详情→家长绑定→会员卡 | 新增/列表/详情同库 OK；**会员卡独立库** | ⚠️ 60% |
| 学员：办卡→充值→消耗→剩余课时 | 卡库独立；**扣课时假** | ❌ 30% |

## 五、检测目标（如何逐项验证问题存在）

> 以下均为"打开两个页面对比"即可复现的验收级检测，建议按序执行。

1. **学员假更新**：学员管理 → 编辑某学员姓名保存 → 返回列表**重新进入** → 姓名是否还原（预期还原=假更新）
2. **学员假删除**：删除一个学员 → 重新进入列表 → 该学员是否还在（预期还在=假删除）
3. **排课不落库**：排课页新建一条排课并保存 → 进入周课表/日历 → 是否出现新排课（预期不出现）
4. **班级不落库**：课程页新建班级 → 返回班级列表重新拉取 → 是否有新班级（预期没有）
5. **消课不扣课时**：某学员剩余课时 X → 消课 2 节 → 该学员课时详情 → 是否变成 X-2（预期不变）
6. **办卡不联动**：会员管理办一张卡/充值 → 学员详情"剩余课时" → 是否增加（预期不增加）
7. **薪资不汇总**：本周实际上课 5 节 → 薪资页自动计算 → 是否体现 5 节课时费（预期不体现）
8. **统计不动**：新增 10 个学员后 → 数据中心/首页统计 → 学员总数是否变化（预期不变）
9. **线索不转化**：线索转正 → 学员列表 → 是否有该正式学员（预期没有）
10. **教师双库**：教师管理新增一位老师 → 排课页选择老师列表 → 是否出现该老师（预期可能不出现）

## 六、验收标准（打通后的"应该"）

> 每一条对应上面一个检测目标，全部通过 = 业务真正连起来。

| # | 验收标准 |
|---|---|
| 1-2 | 学员编辑/删除后，任意页面重新进入，数据保持已改/已删状态（同会话内存态一致） |
| 3 | 新排课立即出现在周课表/日历，且可作为课次生成依据 |
| 4 | 新班级立即出现在班级列表，并可继续选学员/排课 |
| 5 | 消课后学员剩余课时实时扣减，课次记录与课时余额一致 |
| 6 | 办卡/充值后学员剩余课时联动增加（可设计为"充值→课包+课时"的转换规则） |
| 7 | 薪资可按课时明细自动汇总（课时费模板 × 实际上课记录） |
| 8 | 统计数字由业务实体聚合得出（学员数=STUDENTS.length，课次=LESSON_RECORDS 计数等） |
| 9 | 线索转正后生成正式学员，来源线索可回溯 |
| 10 | 全项目教师数据单一来源，教师管理/排课/班级引用同一份 |

**统一原则（验收底线）**：
1. **单一数据源**：每个实体只有一个"库"，所有 service 读写同一份
2. **写必回写**：所有 create/update/delete/扣减 都必须真实修改共享数组（内存态即可，刷新重建）
3. **跨库联动**：会员卡→课包、薪资→课次、统计→实体 必须由"转换/聚合逻辑"而非"独立静态数据"驱动
4. **store 收敛**：核心实体（学员/班级/课程/排课）统一走 store，页面不裸调 service

## 七、整改路线建议（仅规划，未实施）

| 阶段 | 内容 | 工作量预估 |
|---|---|---|
| **阶段 A（止血）** | 统一"写回"策略：补全 update/delete/deduct 的真实数组修改（学生/排课/班级/课包扣减）；教师/学员/班级/课程模板统一到单一数据源 | 中 |
| **阶段 B（打通）** | 会员卡→课包转换、薪资←课时聚合、统计改由实体聚合、线索→学员转化 | 中 |

**风险提示**：阶段 A/B 会改动大量 data 函数，建议为每个实体先写"创建→更新→删除→重新读取"的冒烟脚本，避免回归。
