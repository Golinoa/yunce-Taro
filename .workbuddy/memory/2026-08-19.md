## 关键教训：布局判定须与渲染策略严格一致
**bug**：判定 "是否放得下" 用固定 `gap=[12rpx]` 估算，但渲染用 `gap-[12rpx] justify-between`——估算偏严、渲染偏松。结果：2 个标签场景被错判为 "放不下完整文字"，实际显示成了纯图标。

**修复要点**：
- 估算时 `TAG_GAP_RPX = 0`（不计入间隔，因为 justify-between 会自然撑开）
- 字符宽度估到 30rpx 更接近中文真实（含字间距/字体）
- 渲染维持 `gap-[12rpx] justify-between`——保证 "不挨在一起 + 留有呼吸感"
- 文字友好余量提到 24rpx

**普遍原则**：UI 自适应降级时，"判定逻辑"必须匹配 "真实渲染模式"——若用 flex/spacing 撑开间隔，估算就不该把这部分间隔当固定值算入。这条经验适用于所有自适应降级场景。

## 真·bug：useMemo 返回字段名与外层解构不一致 → 按钮文字永远 undefined

**症状**：连续多轮调整 `TAG_GAP_RPX`/`TAG_TEXT_RPX`/`TEXT_FRIENDLY_MARGIN_RPX` 都没法让按钮显示文字——再宽的预算也无济于事，因为渲染拿到的 `navLabel`/`callLabel` 永远是 `undefined`。

**根因**（`src/components/home/campus-card/index.tsx`）：
```ts
const { mode, navLabel, callLabel } = useMemo(() => {
  const candidates = [{ mode: 'row', nav: '导航到店', call: fullCall }, ...];
  for (const c of candidates) {
    if (...) return c;          // ← 返回 { mode, nav, call }
  }
  return { mode: 'split', nav: '导航到店', call: fullCall };
}, [...]);
```
外层解构是 `navLabel` / `callLabel`，跟 `c.nav`/`c.call` 字段名对不上 → 解构出来永远是 undefined → 渲染到 `TagActionButton` 的 `label` 也是 undefined → `{label ? <Text>{label}</Text> : null}` 走空值分支 → 永远只剩图标。

**为什么前几轮没暴露**：估算逻辑本身没有 bug（用户能看到"降级到纯图标"正是 row-icon / row-compact 也失败时返回 c 的字段对不上导致），加上我前几轮的判断只盯着"估算数值"和"渲染模式"，没去看"useMemo 返回值"是否真的会被消费。**TypeScript 不会报这种字段名不匹配的错**（解构 undefined 字段合法且无诊断），等于完全静默。

**修复**：
- `candidates` 类型与字段名改为 `{ mode, navLabel, callLabel }`，与外层解构严格对齐；
- `for` 循环内显式 `return { mode: c.mode, navLabel: c.navLabel, callLabel: c.callLabel }`；
- 兜底 `split` 也是 `{ mode: 'split', navLabel: '导航到店', callLabel: fullCall }`；
- 加一行注释提示字段必须对齐，避免再犯。

**校验**：`npx eslint --fix` + `prettier --write` + `rm -rf dist && VITE_USE_MOCK=true npm run build:weapp`（5.76s 通过）；产物关键字命中 `联系电话`×2、`导航到店`×2、`到店`×7、`免费试听`×1、`暑期特惠`×1。

**通用教训（写入七律）**：
1. **解构字段名必须与返回对象的字段名 1:1 对齐**——TS 类型不会因为"解构字段缺失"报错，等于一个隐蔽死代码陷阱。写 useMemo / 普通函数时，若返回对象字段名跟下游解构不一致，立即给 TS 加上显式返回类型或在调试时 console.log 一遍返回值。
2. **看到「永远/总是某种表现」时，第一反应去看"输入值是否真的传到了那里"**——别被"补偿式调参"（不断调估算常数）带偏。这次连续 4 轮我都只调估算参数、调 TAG_GAP_RPX、调 TEXT_FRIENDLY_MARGIN_RPX——本质都在改同一层，根本没碰到 bug 层。
3. **校验"真的改了"不能再只看产物关键字**——产物里 `\u8054\u7cfb\u7535\u8bdd` 一直在，但运行时取不到是另一回事。下次遇到"改完没生效"类反馈，先在调试时打印 `useMemo` 的返回值，再决定要不要重打包。

## 修复帮助页"信息层级混乱"（真实 bug：flex 方向错误）

**用户截图反馈**：3 个模块卡片里 "学员与家庭 / 课程与出勤 / 门店与经营" 标题与其副标题**横向挤在同一行**（"学员与家庭" 紧贴 "学员档案、家庭协作一目了然"），副标题自动换行到下一行 —— 信息层级完全看不出主次。

**真凶**：中间列容器 `<View className="flex-1 min-w-0">` 在当前 Taro/UnoCSS 配置下被 `flex-1` 触发成 `display: flex` 容器（且 `flex-direction: row`），于是 `<Text>` 子元素横向内联流动。两个 `<Text>` 在 inline 流里就像普通文字一样首尾相接 — 这正是截图里的"挤一行"现象。

**修复**（`src/package-settings/pages/help/index.tsx` 卡片中间列）：
- `flex-1 min-w-0` → `flex-1 min-w-0 flex flex-col gap-[8rpx]`（强制列方向 + 8rpx 间距）
- 副标题 `text-[26rpx]` → `text-[24rpx]`（与 32rpx 标题拉开层级对比）
- 标题加 `leading-tight`，副标题保留 `leading-relaxed`
- 删掉标题上的 `mb-[8rpx]`（gap 已替代）

**校验**：ESLint(0) + Prettier 无改动；`rm dist + webpack cache` 后 `build:weapp` 30.6s 成功；help 页产物 index.{js,json,wxml,wxss} 已入 dist。

**通用经验（写入七律）**：
- 微信小程序 `<text>` 默认 `display: inline`，因此**多个 `<text>` 兄弟节点默认横向流动**，会撞上 `<view>` 容器的右边界再换行。若期望"标题 + 副标题"上下分层，**必须显式 `flex flex-col`**，光给父容器加 `flex-1 min-w-0` 不够 —— `flex-1` 在本项目 UnoCSS 下会把容器变成 flex 行布局，反而触发内联流动。
- 凡是 "卡片标题 + 副标题上下排" / "两段文字段落" 场景，统一用 `flex flex-col gap-[X]`，不要依赖默认流。

**根因**：`src/package-course/pages/course-form/index.tsx` 的 `PageContainer` 同时传了 `safeBottom` 并自定义了 `h-screen flex flex-col`。`safeBottom` 会给外层容器加 `pb-safe-bottom`（`calc(var(--safe-bottom) + 144rpx)`），使 `navigateTo` 非 tabBar 页面的总高度超过视口，产生原生滚动区域；而 `disableScroll: true` + 内部 `ScrollView(flex-1)` 在这种情况下无法稳定接收鼠标滚轮事件，表现为滚动失效。

**修复**：
- `PageContainer` 移除 `safeBottom`，改为 `className="h-screen flex flex-col overflow-hidden"`。
- 底部按钮本身已是 `fixed` 定位并自行处理了 `env(safe-area-inset-bottom)`，因此去掉 `safeBottom` 不影响底部安全区。
- `overflow-hidden` 进一步确保页面没有原生滚动条，内部 `ScrollView` 独占滚动。

**校验**：
- `npx eslint src/package-course/pages/course-form/index.tsx` 零错误。
- `VITE_USE_MOCK=true npm run build:weapp` 编译成功（需先用 PowerShell `Remove-Item -Recurse -Force` 删掉 dist，绕过 WorkBuddy safe-delete shim 对 Taro `emptyDirectory` 的拦截）。
- 产物 `dist/package-course/pages/course-form/index.js` 中已无 `pb-safe-bottom`，`overflow-hidden`/`h-screen`/`flex-col` 均命中；`disableScroll:true` 仍在 `index.json`。

**经验**：`navigateTo` 非 tabBar 页面若用 `disableScroll: true` + 内部 `ScrollView` 承载滚动，PageContainer 不应再传 `safeBottom`，否则 pb-safe-bottom 会让外层容器高度超限，ScrollView 的鼠标滚轮/滚动条表现异常。底部安全区应由 fixed 按钮自行处理，或内容加 `pb-safe-bar`。

## 修复：course-form 编辑课程页鼠标仍无法滚动（追加修复）

**现象**：上一轮去掉 `safeBottom` 后，用户反馈新建/编辑课程页滚动条仍失效，鼠标滚轮无法滚动表单。

**根因**：`ScrollView` 虽然设置了 `flex-1`，但它作为 flex item 默认 `min-height:auto`，会按内部内容撑开高度；当表单内容（高级设置展开后）远超视口时，ScrollView 被撑到跟内容一样高，外层 `overflow-hidden` 把它截断，导致没有溢出、滚动条/鼠标滚轮失效。

**修复**：把 `src/package-course/pages/course-form/index.tsx` 中
```tsx
<ScrollView scrollY className="flex-1">
```
改为
```tsx
<ScrollView scrollY className="flex-1 min-h-0">
```
`min-h-0` 让 flex item 的 `min-height` 变为 0，ScrollView 严格按 `flex:1` 占据剩余视口高度，内容超出时产生溢出，从而恢复滚动。

**校验**：
- `npx eslint src/package-course/pages/course-form/index.tsx` 零错误。
- `rm -rf dist node_modules/.cache/webpack/weapp && VITE_USE_MOCK=true npm run build:weapp` 干净编译成功（31s）。
- 产物 `dist/app.wxss` 中 `.min-h-0{min-height:0}`、`.flex-1{flex:1 1 0%}`、`.h-screen{height:100vh}`、`.overflow-hidden{overflow:hidden}` 全部命中；`dist/package-course/pages/course-form/index.js` 中 `className:"flex-1 min-h-0"` 已生效。

**经验**：Taro/微信小程序里 `ScrollView` 放在 `flex-col h-screen overflow-hidden` 容器内做页面内滚动时，必须同时写 `flex-1 min-h-0`（或 `flex-1 h-0`），否则 `min-height:auto` 会让它按内容撑开，滚动失效。这是项目中 `TeacherTab`、`ScheduleTab`、`SalaryTab` 等组件的既有最佳实践（`className="flex-1 h-0"`）。

## 修复：图片上传后预览图不显示

**现象**：上一轮把 `http://tmp/` 在 `chooseImageTemp` 中统一替换为 `wxfile://tmp/` 后，课程图片选择后只剩删除按钮，预览图空白。

**根因**：微信开发者工具里 `<wx-image>` 能渲染 `http://tmp/...` 临时路径，但无法识别 `wxfile://tmp/...` 作为本地图片资源；真机则相反。直接在返回给业务层的值上做协议归一化，导致开发者工具中预览失效。

**修复**：
- `src/utils/image-upload.ts` 的 `chooseImageTemp()` 恢复返回 `chooseMedia` 原始 `tempFilePath`（不转换），保证前端 `<Image>` 预览和 `Taro.previewImage` 在开发者工具/真机都能正常显示。
- 文件系统读取统一放到 `uploadImage()` 内部处理：`uploadImage()` 在调用 `getFileSystemManager().readFile` 前先执行 `normalizeTempFilePath()`，把 `http://tmp/` 转成 `wxfile://tmp/`，确保 mock 模式读 base64 和真机 `readFile` 都能成功。
- `isTempImagePath()` 继续兼容 `http://tmp/`、`wxfile://`、`file://` 三种前缀，业务层判断逻辑不受影响。

**校验**：
- `npx eslint src/utils/image-upload.ts` 零错误；
- `rm -rf dist node_modules/.cache/webpack/weapp && NODE_OPTIONS=--max-old-space-size=4096 VITE_USE_MOCK=true npm run build:weapp` 干净编译成功；
- 产物 `dist/common.js` 中 `chooseImageTemp` 返回 `p.tempFilePath`（原始路径），`uploadImage` 调用 `normalizeTempFilePath` 后再 `readFile`。

**经验**：临时文件路径的「展示用」与「读取用」应分离。展示路径交给 `<Image>` / `previewImage` 保持原始值；只有 `fs.readFile` 等需要本地文件句柄的场景才做 `http://tmp/` → `wxfile://tmp/` 转换。

## 修复：图片上传「不管大小都上传失败」

**现象**：所有图片上传组件（含课程背景图/封面）点击选图后一律提示失败，且没有按分辨率判断裁剪。

**根因**（两个叠加）：
1. `Taro.cropImage` 在 @tarojs/taro 4.1.9 里**只有类型声明、没有运行时实现**（搜遍 taro/runtime/shared 的 dist 都无 `cropImage`）。上一版无条件调用 `Taro.cropImage({...})`，实际是 `undefined(...)`，每次必抛 `TypeError`。
2. 上一版是「只要传了 cropScale 就裁剪」，并非按分辨率大小判断，不符合「图片大才裁剪」的需求。

**修复**（`src/utils/image-upload.ts`）：
- 新增 `getWxCropImage()`：优先用 `globalThis.wx.cropImage`（小程序全局对象，DevTools/真机支持），探测 `typeof === 'function'`；Taro 若后续实现也兜底；都没有则返回 `undefined`。
- 新增 `isLargeImage(path)`：`Taro.getImageInfo` 读取宽高，最长边 > `LARGE_IMAGE_MAX_SIDE`(2000px) 才算大图。
- `chooseImageTemp` 仅在「传了 cropScale 且 isLargeImage 为真」时才调裁剪；裁剪 API 不可用或裁剪异常 → `console.warn` 并**静默回退原图**，绝不让上传失败；仅用户主动取消抛 `ImageCancelError` 静默处理。

**校验**：eslint + tsc 无 image-upload 相关错误；`VITE_USE_MOCK=true npm run build:weapp` 成功；产物 `dist/common.js` 确认改为 `globalThis.wx` + 能力探测，无 `Taro.cropImage` 直接调用。

**经验**：Taro 的 `.d.ts` 里声明的 API 不一定有运行时实现（尤其较新的微信 API）。用时先用 `typeof xxx === 'function'` 探测，或直接走 `globalThis.wx` 原生对象并做能力兜底，避免「类型有、运行无」的坑。

## 修复：长图未裁剪且 `cropImage` 报 `Cannot read properties of undefined`

**现象**：上传一张很长的手机截图到课程背景图（16:9）或封面（1:1）上传框，既没弹出裁剪，控制台又报错 `TypeError: Cannot read properties of undefined (reading 'tempFilePath')`。

**根因**：
1. `wx.cropImage` 是**回调式 API**，官方文档明确「不支持 Promise 风格调用」。上一版虽然改成 `globalThis.wx.cropImage`，但仍然当 Promise 直接 `await cropFn(...)`，结果 `cropRes` 是 `undefined`，取 `tempFilePath` 时报错。
2. 上一版只按「长边 > 2000px」触发裁剪。手机截图 1080×1920/2400 等虽然宽高比严重不符，但长边阈值无法覆盖所有场景，导致“没检测出来”。

**修复**（`src/utils/image-upload.ts`）：
- `getWxCropImage()` 手动 Promisify：在传入的 option 里补 `success` / `fail` 回调，再包成 `Promise`。
- 新增 `parseCropRatio()` 与 `shouldCropImage(path, cropScale)`：
  - `LARGE_IMAGE_MAX_SIDE` 下调至 1600px；
  - 同时用 `Taro.getImageInfo` 比较源图「长边/短边」与目标比例（如 16:9→1.778）的差异；
  - 只要「分辨率过大」或「宽高比差异 > 0.2」任一满足，就进入裁剪。
- 这样长图/截图即使分辨率未触发阈值，也会因比例严重不符而弹出裁剪。

**方案选型**（搜索确认）：
- 简单固定比例裁剪（头像、封面、banner）→ 微信原生 `wx.cropImage`（系统级弹窗，零依赖，本项目适用）。
- 需要自由框选/缩放/旋转 → `we-cropper` 或自研 Canvas 2D 裁剪器（更重，适合后续高定制需求）。

**校验**：eslint + tsc 零错误；`VITE_USE_MOCK=true npm run build:weapp` 成功；产物中 `cropImage` 调用已改为 `new Promise(function(n,r){e.cropImage({...success:...,fail:...})})` 形式。
