## 编译「卡死」真因与解决（本会话关键排查）

- **现象**：`npm run build:weapp` 每次都“卡住”——超时、产物残缺、或随机报 `ENOENT: no such file ... dist/.../index.js`。
- **真因**：之前多次编译任务在 `TaskOutput` 被用户中断后，后台 `node`/`taro` 进程**没有完全退出**，变成僵死进程（实测有进程从下午 14:42 / 16:09 一直跑到次日凌晨，长达 9~11 小时）。它们持续占着 CPU/内存、锁着 `dist` 与编译日志文件；新开的编译与僵死编译抢同一个 `dist`，互相覆盖 → 卡死 / 残缺 / ENOENT。
- **排查线索**：`ps aux | grep node` 看到残留 node 进程；`rm` 旧日志报「另一个程序正在使用此文件，进程无法访问」，说明文件句柄被后台任务宿主（PowerShell/node）锁住。
- **解决步骤（已验证有效）**：
  1. `TaskStop` 停掉所有残留后台编译任务（其中一个 `build:weapp:clean` 跑了 39 分才被强杀）。
  2. 确认 `ps` 无残留 `node`/`taro`/`webpack` 进程。
  3. `rm -rf dist node_modules/.cache/webpack/weapp` 清掉半成品 + 被中断的 clean 编译写残的 webpack 缓存。
  4. **用 PowerShell 跑编译，不要用 Git Bash**：Git Bash 下 Taro 并行 emit 资源会随机 `ENOENT`；PowerShell 稳定。
  5. 日志 `2>&1 | Tee-Object -File build-final.log` 实时落盘（注意：PowerShell `Write-Host` 不进 `Tee-Object` 文件，退出码要看任务状态）。
- **验证产物的坑（避免误判）**：Taro 3 渲染走 `base.wxml` 的 `taro_tmpl`，组件**不会**生成独立 `dist/components/<Name>/` 目录（正常）；组件代码在 `common.js`/页面 `index.js` 里，中文被压缩为 `\uXXXX` 转义，字面量 grep 搜不到是正常的。确认方法：搜 `StudentMultiSelectSheet`、`resolveEffectiveSubjectId`、`fillHeight`，以及中文转义 `u672a`(未) `u6392`(排) `u73ed`(班) `u7559`(留) `u7a7a`(空)。

## 图片上传 / 裁剪「闪一下消失」根因与修复
- **现象**：手机上传图片、裁剪后预览「闪一下就没有」，再上传又好了、再传又闪。
- **根因**：组件把 `chooseImageTemp` 返回的**微信临时路径**（`http://tmp/`/`wxfile://tmp/`）直接当预览 `src`；该临时文件生命周期不可靠，页面切换或系统回收存储后即失效。上一轮用 `wx.saveFile` 持久化是错误方案——FileSystemManager.saveFile 受 **10MB 本地存储配额且累加计数**，传几张配额耗尽就回退临时路径，导致问题复发。
- **正确修复**（已落地 `src/utils/image-upload.ts`）：选图/裁剪完成后**立即把临时文件 `fs.readFile` 读成 base64 Data URL 固化返回**（`tempFileToBase64`）。base64 在内存中永不回收，预览/上传都稳定。`uploadImage` 增加 `data:` 前缀直通判断，避免对已 base64 再次读取。`shouldCropImage` 仍按「长边>1600px 或 宽高比差异>0.2」决定是否调 `wx.cropImage`，cropScale 仅限 Taro 类型允许值（'1:1'/'16:9'/'3:4'/'4:3'/'4:5'/'5:4'/'9:16'）。
- **验收**：`chooseImageTemp` 现在返回 base64；`data/*` 里 `isTempImagePath` 对 base64 返回 false → 保存时原样回传，不再二次读文件。`eslint`/`tsc` 通过，增量编译成功。

## `backgroundfetch privacy fail` (errno 101) 真因与处理
- **此报错不是我们代码触发的**，是微信客户端启动时**系统级自动发起**的「后台数据预拉取」(`private_getBackgroundFetchData`)，不受 app 内 `onNeedPrivacyAuthorization` 流程管控。
- **根因**：`errno:101 jsapi invalid request data` = 小程序《个人信息保护指引》在**微信公众平台后台（mp.weixin.qq.com）没配置/没通过**，隐私系统接口拿到非法数据，系统预拉取失败。
- **性质**：微信开放社区公认**无害噪音**，普遍出现在**真机调试**，体验版/正式版不受影响、功能正常。纯代码层无法消除（系统自己发起）。
- **彻底消除前提**：在 mp.weixin.qq.com 配置并通过《个人信息保护指引》隐私协议；用户经我们弹窗（或微信自身流程）授权后，隐私 consent 状态建立，后续预拉取不再 101。首次启动授权前仍可能闪一次。
- **与我方弹窗的关系**：我们 `initPrivacy` 弹窗处理的是「我们业务代码实际调用的隐私接口（如 chooseLocation）」的授权，正确且必要；但它不能阻止系统预拉取那次首启调用。
